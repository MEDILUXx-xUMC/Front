# FE 협업 규칙

## 1. 첫 작업과 담당 범위

- 로컬 실행과 검사는 [README](../README.md)를 따른다. 프레임워크, 라우팅, 패키지 매니저 등 공통 설정을 바꿀 때는 담당자 한 명이 PR을 올린다.
- 기존 작업 목록 한곳에 **Figma 번호와 화면명, 담당자, 변경할 공통 파일, 선행 작업, PR 링크**를 기록한다. 진행 중에 새 화면이나 공통 파일이 범위에 들어오면 목록부터 갱신한다.
- 화면이나 공통 작업마다 담당자 한 명을 둔다. 화면 간 이동, 인증 흐름처럼 여러 화면이 걸린 작업은 변경을 끝까지 맡을 사람을 정하고 작업 목록에 영향받는 화면을 적는다.

| 작업 범위 | 담당 기준 |
| --- | --- |
| 화면 전용 컴포넌트, 상태, 스타일 | 해당 화면 담당자가 수정한다. |
| 공통 `Button`, `Chip`, `Tag`, 디자인 토큰 | 공통 UI 작업별로 정한 담당자가 수정한다. 사용하는 화면과 필요한 옵션을 먼저 확인한다. |
| 라우트 등록, 앱 진입점, 인증, 공통 요청 처리 | 변경마다 담당자 한 명이 수정한다. 화면 담당자는 필요한 경로와 진입 조건을 작업 목록에 적는다. |
| 공유 타입, 기능별 API 모듈과 Mock | 같은 기능을 사용하는 화면 담당자끼리 수정 범위를 확인하고, 변경을 맡을 사람을 한 명 정한다. |
| 프로젝트 설정, 의존성, lockfile | 설정을 바꾸는 PR 담당자가 수정한다. 설치나 실행 방식이 달라지면 PR에 새 명령을 적는다. |

## 2. 공통 파일을 변경할 때

1. 수정 전에 팀 채널에 **파일 또는 모듈, 바꾸려는 내용, 영향받는 화면, 먼저 병합해야 할 PR**을 남긴다. 관련 담당자가 이미 수정 중이면 한 사람이 변경을 맡고 병합 순서를 정한다.
2. 두 화면이 같은 변경을 기다리면 공통 변경을 작은 PR로 먼저 올린다. 화면 담당자는 독립적으로 진행할 수 있는 화면 작업을 하고, 공통 PR이 병합되면 최신 `main`을 반영해 연결한다.
3. 공통 컴포넌트의 기본 동작이나 공유 함수의 인자를 바꿀 때는 기존 호출부를 검색한다. 기존 호출 방식이 유지되도록 옵션을 추가할 수 있으면 공통 PR을 먼저 병합한다. 기존 호출 방식도 바뀌어야 하면 호출부까지 같은 PR에서 수정하고 해당 화면 담당자와 함께 검증한다.

예를 들어 예산 화면과 상품 목록이 모두 `Chip`에 선택 상태를 요구하면, 공통 UI 담당자가 두 화면에서 필요한 동작을 확인한 뒤 `Chip` PR을 올린다. 두 화면은 그 PR이 병합된 뒤 같은 속성으로 연결한다.

## 3. 코드와 화면 이름

| 항목 | 규칙 |
| --- | --- |
| 언어와 타입 | 새 코드는 TypeScript로 작성한다. 여러 기능에서 사용하는 `Product` 같은 타입은 `src/types/`에 한 번만 정의한다. 한 컴포넌트에서만 쓰는 타입은 해당 파일에 둔다. |
| 화면 이름 | 작업 목록과 PR 본문에 Figma 번호와 화면명을 함께 적는다. 라우트 경로와 파일명은 라우팅 방식을 정할 때 맞추고, 이동 경로를 바꾸는 PR에는 영향받는 진입 화면을 적는다. |
| 이름 표기 | 변수, 함수, 객체 속성, API JSON 키는 `camelCase`를 사용한다. 예시는 `productId`, `depositAmount`, `rentalDays`다. 컴포넌트와 타입은 `ProductCard`, `BudgetScreen`, `Product`처럼 `PascalCase`를 사용한다. |
| 공통 UI | 공통 UI를 가져다 쓰는 화면은 공개된 속성으로 상태와 동작을 전달한다. 새 옵션은 담당자와 이름, 기본값, 사용 화면을 확인한 뒤 추가한다. 한 화면에만 필요한 UI는 해당 화면에서 관리한다. |

## 4. API와 Mock을 맞추는 방법

- 화면은 `src/api/`의 기능별 함수로 요청한다. 기본 URL, 인증 헤더, 공통 오류 처리는 API 모듈에서 관리한다. 화면은 필요한 로딩·성공·빈 결과·오류 상태를 표시한다.
- 구현·연동 전에 BE 담당자와 같은 API 문서에서 **HTTP 메서드와 경로, 인증·권한, 요청 필드, 성공·오류 상태 코드와 응답 예시, 필수·선택과 `null` 허용 여부**를 맞춘다. 목록은 빈 응답을 확인하고, 페이지 구분이 있으면 요청값, 기본 정렬, 다음 페이지 판단 기준도 확인한다. 화면에서 오류 종류를 구분해야 하면 분기에 사용할 오류 코드를 BE와 맞춘다.
- 계약이 바뀌면 BE 담당자와 변경 항목, 영향받는 화면, 기존 FE와의 호환 여부, 적용 시점을 확인한다. 호환되는 전환이 가능하면 새 형식을 제공하는 BE 배포 → FE 전환 → 이전 형식 제거 순서로 진행한다. 두 형식을 함께 지원하기 어려우면 전환 일정을 합의하고 작업 목록에 적는다.
- FE는 API 함수, 요청·응답 타입, Mock을 같은 PR에서 갱신하고, 반환값을 사용하는 화면을 확인한다. FE·BE PR에 같은 API 문서를 연결하고, 상대 PR이 생기면 연결해 선행 작업과 배포 순서를 확인할 수 있게 한다.
- Mock 응답에 실제 API와 같은 필드 구조와 타입을 사용한다. 화면은 Mock과 실서버에서 같은 API 함수와 반환 타입을 사용한다. 연동 시 실제 응답으로 정상 흐름, 빈 결과, 화면에서 처리하는 오류를 확인한다. 문서나 Mock과 응답이 다르면 합의한 계약을 기준으로 수정 담당자를 정한다.

| 데이터 | 합의 기준 |
| --- | --- |
| 금액 | 원 단위 정수 `number`를 사용한다. `15000`으로 주고받고 화면에 `₩15,000`으로 표시한다. |
| 날짜 | 달력 날짜는 `YYYY-MM-DD`로 주고받고 같은 날짜를 한국어 형식으로 표시한다. |
| 시각 | 시간대를 포함한 ISO 8601 문자열을 사용한다. 예시는 `2026-11-14T03:30:00Z`다. 화면에서 `Asia/Seoul` 기준으로 변환해 표시한다. |

## 5. 브랜치, 리뷰, 병합

1. 최신 `main`에서 기능별 브랜치를 만든다. 예시는 `feat/budget-screen`, `fix/product-list`다. PR 하나에 작업 목록의 변경 목적 하나를 담는다.
2. PR에는 작업 목록 링크 또는 Figma 번호와 화면명, 변경 내용, 영향받는 공통 파일이나 화면, 선행 PR(있는 경우), 확인 방법을 적는다. 화면이 바뀌면 캡처를 첨부한다.
3. 다른 FE 한 명이 리뷰한다. 작성자는 프로젝트에 설정된 검사 명령을 실행하고, 바뀐 화면의 진입부터 주요 동작까지 확인한다. 공통 코드 변경은 이를 사용하는 화면 한 곳 이상에서 기존 동작도 확인한다.
4. 병합 직전에 `main`의 새 변경을 확인한다. 뒤처졌으면 작업 브랜치에서 `git fetch origin`과 `git merge origin/main`을 실행한 뒤 검사를 다시 돌린다. 동기화 과정에서 리뷰받은 동작이 바뀌면 해당 부분을 다시 보여준다. 선행 PR이 병합됐고 리뷰와 검사가 끝나면 `main`에 병합한다.

## 6. 충돌이 났을 때

1. PR 작성자가 작업 브랜치에서 충돌 파일을 확인한다. 화면 전용 파일은 화면 담당자가 해결하고, 공통 파일은 변경 의도를 양쪽 담당자와 확인한 뒤 작성자가 해결한다.
2. 한쪽 파일 전체를 선택하기 전에 양쪽 변경이 필요한 이유를 확인한다. 같은 라우트나 공통 속성을 서로 다르게 바꿨다면 사용할 이름과 동작을 먼저 합의하고 관련 호출부까지 수정한다. lockfile은 의존성 선언을 먼저 정리한 다음 팀이 정한 패키지 매니저로 다시 생성한다.
3. 충돌 해결 후 프로젝트 검사와 관련 화면 동작을 다시 확인한다. PR에 해결한 파일과 결정한 동작을 남겨 리뷰어가 확인할 수 있게 한다.
